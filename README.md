# Predictive Maintenance for Industrial Equipment

Predict whether a machine will **fail within the next 24 hours** from its sensor readings and maintenance
history, score every machine with a **risk score**, and **alert** the maintenance team about high-risk equipment.

* Live Streamlit app: _add your link here after deploying_
* Static dashboard (GitHub Pages): _https://puneeth7104.github.io/Predictive-Maintenance-for-Industrial-Equipment/_
* Detailed report: _https://github.com/Puneeth7104/Predictive-Maintenance-for-Industrial-Equipment/blob/main/Predictive_Maintenance_For_Industrial_Report.pdf_

> The data is **synthetic** (generated by `src/generate_data.py`), because no real dataset was provided.
> It mimics real behaviour: temperature and vibration rise and pressure drops in the hours before a failure,
> some failures are sudden, some cycles end with planned maintenance, and some sensor readings are missing.

## What the project does

| Step | File | What happens |
|---|---|---|
| 1. Collect data | `src/generate_data.py` | 20 machines x 180 days of hourly temperature, vibration, pressure, operating hours + a maintenance log |
| 2. Features | `src/features.py` | rolling mean/std/min/max, lag differences, drift from each machine's own baseline - **past data only (no leakage)** |
| 3. Label | `src/features.py` | `label = 1` if a failure happens in the next 24 h |
| 4. Train | `src/train.py` | 5 models; rare failures handled with class weights and undersampling; chronological train/validation/test split |
| 5. Evaluate | `src/train.py` | precision, recall, F1, PR-AUC, ROC-AUC, failures caught, lead time, false alarms per machine-week |
| 6. Risk scores | `src/risk_scoring.py` | latest risk (Low / Medium / High) per machine + 14-day history + main driver |
| 7. Monitoring | `app.py`, `docs/index.html` | Streamlit app and a static GitHub Pages dashboard |
| 8. Alerts | `src/alerts.py` | Slack webhook + e-mail (SMTP); safe dry-run when nothing is configured |

## Results (test set = most recent ~6 weeks, never used for training or tuning)

Selected model: **Gradient Boosting (class-weighted)**, chosen on validation PR-AUC.

| Metric | Value |
|---|---|
| Precision | 0.92 |
| Recall (risky hours) | 0.65 |
| PR-AUC | 0.78 (no-skill baseline = 0.03) |
| ROC-AUC | 0.95 |
| Failures with an alert before they happened | 22 of 22 (mean warning ~16 h) |
| False-alarm episodes | 2 in 6 weeks (0.02 per machine-week) |

Recall per hour (0.65) is below the 0.80 validation target: the alert threshold was tuned on older data and
sudden failures give the model little warning. Details and discussion are in the report.

## Run it locally (Windows / Mac / Linux)

```bash
git clone https://github.com/Puneeth7104/Predictive-Maintenance-for-Industrial-Equipment.git
cd Predictive-Maintenance-for-Industrial-Equipment

python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # Mac / Linux

pip install -r requirements.txt
python run_pipeline.py           # data -> model -> risk scores -> docs/index.html (about 1-2 min)
streamlit run app.py             # opens http://localhost:8501
python -m src.alerts --dry-run   # preview the alert message
python -m pytest                 # optional: pip install pytest first
```

The repository already contains the generated data, trained model and figures, so `streamlit run app.py`
works immediately after `pip install`.

## Deploy

**Streamlit Community Cloud** - go to https://share.streamlit.io -> *Create app* -> pick this repo,
branch `main`, main file `app.py` -> *Deploy*. (If the model cannot be loaded because of a different
scikit-learn version, the app retrains it automatically on first start.)

**GitHub Pages** - repo *Settings -> Pages -> Build and deployment -> Source: Deploy from a branch ->
Branch `main`, folder `/docs`* -> Save. After about a minute the dashboard is live at
`https://puneeth7104.github.io/Predictive-Maintenance-for-Industrial-Equipment/`.

## Alerts (Slack / e-mail)

Set any of these as environment variables, Streamlit secrets (`.streamlit/secrets.toml.example`) or GitHub
repository secrets (*Settings -> Secrets and variables -> Actions*):

`SLACK_WEBHOOK_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `ALERT_FROM`, `ALERT_TO`

* In the app: *Alerts* tab -> **Send alerts now**.
* Automatically: the GitHub Action `.github/workflows/alerts.yml` runs on weekdays (or manually under the *Actions* tab).
* Without credentials everything runs in **dry-run** mode and only writes `data/alerts_log.csv`.
* Never commit passwords - `.streamlit/secrets.toml` and `.env` are in `.gitignore`.

## Limitations

* Synthetic data: real equipment is noisier; retrain on real history before trusting the scores.
* Only 22 failures in the test period, so event-level numbers have wide uncertainty.
* The dashboard shows a replay of the last 14 days of the dataset, not a live sensor feed.
